# ThreatLens Testing Guide

How to verify a ThreatLens deployment, manually and automatically.

## 1. Automated tests

```bash
cd backend  && python -m pytest            # 52 tests: parser, detection rules, auth/RBAC, every API flow
cd frontend && npm run lint && npm test    # ESLint (zero warnings) + Jest unit tests
```

The backend suite runs on an isolated SQLite database with network enrichment stubbed, so it is
fast and deterministic. CI (`.github/workflows/ci.yml`) additionally applies the Alembic migrations
to a real PostgreSQL instance and checks that models and migrations are in sync.

## 2. Environment verification

With `docker compose up -d --build`:

- `docker compose ps` — `db`, `backend` and `frontend` should all be **healthy**.
- http://localhost:8000/health — liveness (`status: healthy`, scheduler running, job timestamps).
- http://localhost:8000/ready — readiness (`database: ok`).
- http://localhost:8080 — the web app.

## 3. Authentication & roles

1. Open http://localhost:8080/dashboard while signed out → you are redirected to `/login`.
2. **Sign up** — the very first account is automatically an **admin**.
3. Sign out (user menu) and sign back in with your username *or* e-mail.
4. A wrong password shows “Invalid credentials”; 10+ attempts per minute are rate-limited (HTTP 429).
5. **Settings → Users** (admin): create an analyst and a viewer. Sign in as the viewer — pages load,
   but analysis, SOAR changes and blocklist edits are rejected with a permission message.
6. Sessions refresh silently: access tokens last 30 minutes, refresh tokens 7 days.

## 4. Threat analysis

1. **Threat Studio** → click the **Mimikatz/LSASS Dump** sample → **Execute AI Analysis**.
2. Expect **Credential Dumping Attempt**, MITRE **T1003 · OS Credential Dumping** (tactic *Credential
   Access*), risk ≥ 80, an incident created and a campaign linked.
3. Tabs: *Behavioral Heuristics* lists every scoring factor; *Automated SOAR Actions* lists rules that
   fired (e.g. *Critical Incident Alert → escalate*); *Global Threat Intel* shows geolocation
   (private/documentation IPs explain why no map is shown).
4. The *AI SOC Analyst Report* is labelled **Generated by AI model** when `GROQ_API_KEY` is set,
   otherwise **Generated by rule engine**.

## 5. Dashboard, cases and campaigns

- **Dashboard** — real 7-day / 24-hour incident trend, open cases, SLA breaches, top attacker IPs and
  telemetry sources.
- **Investigate** — saved views (High Priority, SLA Watch, Unassigned) and per-IP dossiers with a
  merged timeline.
- **Incident detail** — change status / workflow / owner, add notes; each change appears in
  **Settings → Audit Log**.
- **Campaigns** — the seeded attacker `203.0.113.45` shows a single campaign spanning
  Reconnaissance → Initial Access → Credential Access → Lateral Movement → Persistence →
  Defense Evasion → Exfiltration. **Run Correlation** detects the 72-hour slow brute force.

## 6. Integrations

**Settings → Integrations** lists every optional API key from `.env` and whether it is configured.
After adding keys to `.env`, run `docker compose up -d` and refresh the page.

## 7. API

- Swagger UI: http://localhost:8080/docs — click **Authorize** and paste an access token from
  `POST /api/v1/auth/login`.
- Webhook ingestion with the machine key:

  ```bash
  curl -X POST http://localhost:8080/api/v1/logs/webhook \
    -H "X-API-Key: <INGEST_API_KEY from .env>" -H "Content-Type: application/json" \
    -d '{"source":"cisco-asa","logs":["%ASA-2-106001: Inbound TCP connection denied from 203.0.113.50/4444 to 192.168.1.1/80"]}'
  ```

## 8. Database

```bash
docker compose exec db psql -U threatlens -d threatlens
\dt                                   -- 15 tables incl. alembic_version
SELECT username, role, last_login FROM users;
SELECT id, risk_level, threat_type, source, status FROM incidents ORDER BY id DESC LIMIT 10;
SELECT actor, action, timestamp FROM audit_logs ORDER BY id DESC LIMIT 10;
```
